# PRD — Resilient Edge-Intelligence Patient Monitoring Mesh

**Status:** Initial planning
**Date:** 2026-09-28
**Project type:** Academic major project — MedTech + IoT + Computer Networking

## 1. Project vision

Build a real-time, multi-patient monitoring prototype in which patient sensor nodes collect vital signs, perform local risk analysis, and reliably deliver prioritized health telemetry through a resilient local mesh network to an edge gateway and dashboard.

This is an educational/research prototype. It is not a certified medical device and does not replace clinical judgment.

## 2. Problem being solved

Single-device IoT health projects typically fail when connectivity is interrupted, do not distinguish critical alerts from routine telemetry, and provide little measurable networking depth. A ward-like environment needs timely alerts, graceful failure handling, local decision-making, and auditable network performance.

## 3. Target users

### Primary users

### Demonstration users
- A simulated nurse/caregiver viewing the monitoring dashboard.

Real clinical end users, hospital administrators, and patients are **[TBD]** for any future validated version.

## 4. User goals

- Register and identify multiple patient nodes.
- View near-real-time vital telemetry and connection status.
- See a risk state and receive prioritized alerts.
- Continue local monitoring during gateway/network disruption.
- Observe recovery and store-and-forward synchronization after reconnection.
- Measure packet delivery, latency, throughput, reroute time, and recovery completeness.

## 5. Core MVP features

1. **Multi-node sensing:** ESP32-based nodes with heart rate/SpO2 and temperature sensing; ECG is optional and subject to hardware validation.
2. **Local processing:** Filtering, signal-quality indicators, trend/risk scoring, and local critical-event detection.
3. **Resilient local networking:** Local multi-hop or relay-capable network with neighbor/path health, prioritized packets, acknowledgements, and retry handling.
4. **Gateway ingestion:** Gateway receives node packets and forwards normalized telemetry to the backend.
5. **Real-time dashboard:** Patient cards, vital trends, risk state, node connectivity, packet/latency metrics, and active alerts.
6. **Store-and-forward:** Nodes or gateway buffer data during temporary disconnection and synchronize after reconnection.
7. **Alerting:** Critical events are highlighted and delivered to the dashboard; external notification integration is **[TBD]**.
8. **Evaluation mode:** Controlled experiments for node failure, gateway interruption, congestion, and recovery.
9. **Security baseline:** Device identity, authenticated messages, encrypted transport where supported, and no real personally identifiable health data.

## 7. Main user flows

### Setup flow
1. Start gateway and backend.
2. Register or provision a node identity.
3. Pair node with the local network.
4. Assign a simulated patient label.
5. Confirm sensor quality and heartbeat.

### Monitoring flow
1. Node samples and validates signals.
2. Node calculates local status and packet priority.
3. Packet travels through the local network to the gateway.
4. Gateway validates, records, and publishes telemetry.
5. Dashboard updates patient state and trends.

### Failure/recovery flow
1. Operator powers off a relay or blocks the gateway.
2. Nodes continue local scoring and buffer unsent records.
3. Routing retries or selects an available path.
4. Connectivity returns.
5. Buffered data is synchronized with ordering and duplicate protection.
6. Dashboard displays recovery metrics.

### Alert flow
1. A simulated abnormal event is generated by a sensor or test fixture.
2. Node marks the event as high priority.
3. Network applies alert delivery policy.
4. Gateway/backend records the alert.
5. Dashboard shows the alert with timestamp, node, severity, and acknowledgement state.

## 8. Functional requirements

- FR-01: Support at least 6 simultaneously identifiable nodes.
- FR-02: Attach timestamp, node ID, sequence number, signal quality, and priority to telemetry packets.
- FR-03: Detect stale or disconnected nodes within a configurable timeout.
- FR-04: Deliver critical packets with higher delivery priority than routine telemetry.
- FR-05: Prevent duplicate records during retries and synchronization.
- FR-06: Preserve buffered telemetry across temporary network loss for at least 5 minutes in the lab prototype.
- FR-07: Show current and historical readings for each simulated patient.
- FR-08: Record network performance metrics for experiments.
- FR-09: Provide a safe demo/test mode using synthetic or non-clinical data.
- FR-10: Allow operators to acknowledge dashboard alerts.
- FR-11: Never present prototype output as a diagnosis.

## 9. Non-functional requirements

- NFR-01: Dashboard updates should target 2 seconds or less under normal lab conditions.
- NFR-02: Critical alert delivery target: 3 seconds or less on a healthy local network.
- NFR-03: The system must remain usable when one relay node is unavailable.
- NFR-04: Every stored measurement must be traceable to node, timestamp, and sequence number.
- NFR-05: Services must expose health checks and structured logs.
- NFR-06: Code must be testable without physical hardware through simulators/fixtures.
- NFR-07: No production clinical, privacy, or regulatory claims.

## 10. Data requirements

Core entities:

- `devices`: identity, firmware version, capabilities, status, last seen.
- `patients`: simulated label and assignment metadata; real identity fields excluded from MVP.
- `measurements`: timestamp, device ID, patient label, vital values, quality, sequence number, source.
- `alerts`: severity, type, evidence, status, timestamps, acknowledgement.
- `network_events`: route changes, retries, packet loss, latency, disconnects, reconnects.
- `sessions`: experiment/demo start, end, configuration, summary metrics.

Retention policy, database engine, and export format are **[TBD]**.

## 11. Authentication and authorization

- MVP device authentication: provisioned device credentials or pre-shared identity.
- MVP dashboard authentication: lab-only mode without public access; full login is deferred.
- Authorization roles are deferred until Phase 7.
- No real patient identity or clinical account integration in MVP.

## 12. Constraints

- Student budget and locally available hardware.
- Must support live classroom demonstration.
- Must work in a controlled local network without dependence on public cloud.
- Must be explainable in a viva: protocol choices, failure behavior, and measurements must be documented.
- Sensor readings are for prototype evaluation only.
- Hardware selection and final networking protocol are **[TBD]** pending feasibility testing.

## 13. Out of scope

- Clinical diagnosis or treatment recommendations.
- Medical-device certification or hospital deployment.
- Drug dosing, ventilator control, or emergency-service dispatch.
- Non-invasive glucose claims without validated instrumentation.
- Real patient data collection.
- Large-scale public-cloud deployment in MVP.
- Fully autonomous clinical decisions.

## 16. Open decisions

- Hardware bill of materials will be finalized after the Phase 1 hardware spike.
- Local transport spike: ESP-NOW-style application relay; compare against Wi-Fi/Thread/802.15.4 only if the spike fails.
- Backend: Python FastAPI.
- First storage: SQLite; PostgreSQL remains the production-like migration path.
- Dashboard: React + TypeScript.
- Authentication: lab-only mode in MVP; full dashboard auth is Phase 7.
- Alerting: dashboard alerts in MVP; Telegram/SMS is future work.
- ECG and arrhythmia ML are deferred until the core sensing/networking pipeline is reliable.
